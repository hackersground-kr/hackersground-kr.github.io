Azure Portal을 처음 열면 테넌트, 구독, 리소스 그룹이라는 단어가 한꺼번에 등장합니다. 셋 모두 Azure 리소스를 정리하는 단위처럼 보이지만, 실제로는 **사람과 로그인**, **비용과 한도**, **프로젝트의 수명 주기**를 서로 다른 층에서 관리합니다.

이 차이를 알면 “개발 스택마다 리소스 그룹을 만들면 될까?”, “고객사마다 구독을 나눠야 할까?” 같은 질문에 기준을 세울 수 있습니다. 아래 구조를 위에서 아래로 기억해 보세요.

```text
테넌트 (조직의 Microsoft Entra ID)
└── 구독 (청구·권한·한도의 경계)
    └── 리소스 그룹 (함께 관리하고 수명 주기를 맞출 리소스의 묶음)
        ├── App Service
        ├── Storage Account
        └── Application Insights
```

## 테넌트: “누가 우리 Azure에 들어올 수 있나?”

Azure 테넌트는 조직의 **Microsoft Entra ID 디렉터리**입니다. 사용자 계정, 그룹, 앱 등록, 로그인 정책이 이곳에 속합니다. 회사 또는 고객사 하나가 보통 하나의 테넌트를 갖는 이유는 구성원의 신원과 보안 정책을 같은 경계 안에서 관리하기 위해서입니다.

쉽게 말해 테넌트는 건물의 출입 명부입니다. 구독에 접근하려면 먼저 어느 테넌트의 사용자 또는 서비스 주체인지가 정해져야 합니다. 외부 개발자가 작업해야 한다면 계정을 새로 만들기보다 Entra ID의 게스트 초대(B2B)를 이용해 필요한 범위만 권한을 부여할 수 있습니다.

테넌트를 나누는 기준은 “프로젝트 수”가 아니라 **독립된 조직·신원 체계·보안 요구사항**입니다. 고객사 Azure 환경을 대신 운영한다면 고객사의 테넌트를 유지하고, 그 안에서 고객사의 권한 정책에 따라 작업하는 편이 소유권과 감사 기록을 명확하게 합니다.

## 구독: “누가 비용을 내고, 어디까지 쓸 수 있나?”

구독(Subscription)은 Azure 사용량을 청구하고, 지출을 분석하며, 서비스 한도와 정책을 적용하는 단위입니다. 리소스를 만들려면 반드시 하나의 구독에 속해야 합니다. 하나의 테넌트는 여러 구독을 가질 수 있고, 구독 하나에는 여러 리소스 그룹을 둘 수 있습니다.

구독은 다음처럼 비용 또는 운영 책임이 달라질 때 나누기 좋습니다.

- 고객사별로 청구서와 비용 조회를 분리해야 할 때
- 개발·스테이징·운영 환경의 예산과 권한을 강하게 분리할 때
- 샌드박스 실습 비용이 운영 서비스 비용에 영향을 주지 않게 할 때

반대로 앱 하나를 만든다는 이유만으로 구독을 여러 개 만들 필요는 없습니다. 구독이 늘어나면 비용 집계, 권한 설정, 정책 관리도 함께 늘어납니다. 작은 팀이라면 먼저 개발용 구독과 운영용 구독처럼 책임이 분명한 경계부터 시작해도 충분합니다.

## 리소스 그룹: “무엇을 함께 배포하고 관리할까?”

리소스 그룹(Resource Group)은 Azure 리소스를 논리적으로 묶는 컨테이너입니다. 여기서 말하는 묶음은 단순히 기술 스택이 같은 리소스가 아니라, **같은 목적을 위해 만들고 변경하고 제거할 리소스**입니다. 따라서 “개발 스택”이라는 표현은 일부만 맞습니다.

예를 들어 `web-prod-rg`에는 운영 웹앱, 운영 데이터베이스, 모니터링 리소스를 두고, `web-dev-rg`에는 개발 환경의 대응 리소스를 둡니다. 개발 환경을 없앨 때 해당 리소스 그룹을 삭제하면 관련 리소스도 함께 정리할 수 있어 비용 누수를 줄이는 데 도움이 됩니다.

리소스 그룹에는 다음 제약도 있습니다.

- 리소스는 한 번에 하나의 리소스 그룹에만 속합니다.
- 리소스 그룹 안에 다른 리소스 그룹을 넣을 수는 없습니다.
- 리소스 그룹의 위치는 메타데이터가 저장되는 위치이며, 내부 리소스의 배포 지역을 대신 정하지는 않습니다.

공유 네트워크, 공용 모니터링, 여러 앱이 함께 쓰는 Key Vault처럼 수명 주기가 다른 리소스는 별도의 리소스 그룹으로 분리하는 편이 안전합니다. 한 애플리케이션을 지운다고 공유 기반 리소스까지 삭제되는 일을 막을 수 있습니다.

## 고객사 프로젝트에 적용해 보기

가령 `Contoso` 고객사를 위한 웹 서비스를 만든다고 해 보겠습니다. 고객사의 Entra ID 테넌트 안에서 비용 책임이 분명한 `contoso-production` 구독을 사용합니다. 그 안에는 아래처럼 리소스 그룹을 구성할 수 있습니다.

```text
contoso-production 구독
├── contoso-web-prod-rg       # 운영 웹앱과 운영 데이터
├── contoso-web-staging-rg    # 배포 전 검증 환경
└── contoso-shared-prod-rg    # 공용 네트워크·비밀·모니터링
```

개발 환경의 비용과 권한을 별도로 관리해야 한다면 `contoso-development` 구독을 추가하고 같은 패턴을 적용합니다. 고객사가 여러 곳이라면 각 고객사의 테넌트와 구독을 혼동하지 않도록, 이름에 고객사·환경·용도를 일관되게 넣는 것이 좋습니다.

## 만들기 전에 확인할 세 가지

1. **신원 소유자는 누구인가?** 고객사 또는 우리 조직의 테넌트를 확인합니다.
2. **비용과 한도는 어디서 나눌 것인가?** 청구 책임, 예산, 운영 환경을 기준으로 구독을 정합니다.
3. **무엇이 함께 사라져도 되는가?** 같은 수명 주기를 가진 리소스를 하나의 리소스 그룹에 둡니다.

테넌트는 조직의 신원 경계, 구독은 비용과 거버넌스의 경계, 리소스 그룹은 운영 단위라는 역할만 기억해도 Azure 구조를 훨씬 덜 헷갈리게 설계할 수 있습니다. 규모가 커져 구독이 많아지면 그 위에 관리 그룹(Management Group)을 두어 여러 구독에 정책과 권한을 공통 적용할 수 있습니다.
